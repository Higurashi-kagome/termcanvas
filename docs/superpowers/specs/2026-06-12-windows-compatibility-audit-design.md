### 背景

`TermCanvas`在 README 中声明支持 macOS、Linux、Windows，但仓库最近连续出现多次 Windows 相关修复，包括 PTY teardown、pin 附件图片恢复、Unicode git 路径保留等。这说明项目已经具备明确的 Windows 适配需求，同时也暴露出一个事实：Windows 兼容性问题并不是集中在单点，而是分散在终端启动、CLI 包装、路径处理、资源定位、构建安装和测试覆盖等多个链路。

本次工作不直接修复这些问题，也不以“本机完整跑通 Windows 流程”为前提，而是先基于源码做一轮系统化审计，识别会影响 Windows 终端用户安装、启动和核心使用路径的兼容性风险，并把结果整理成可直接进入修复排期的开发视图。

### 目标

- 基于源码对项目现有 Windows 兼容性进行分层审计

- 输出面向开发修复的问题清单，而不是泛泛的体验报告

- 为每个问题提供文件级定位、风险判断依据、修复方向和测试建议

- 区分“确认风险”“可疑风险”“已处理但脆弱”三类结论，避免把所有平台差异都粗暴上升为缺陷

- 形成后续修复工作的优先级输入，帮助开发者按模块而不是按零散现象推进

### 非目标

- 不在本轮直接修改业务代码、脚本或测试

- 不把“Windows 开发者能否完整构建、测试、打包”作为主目标

- 不做以运行结果为主的手工 QA，也不要求本机模拟完整 Windows 用户路径

- 不把 README 或文档中的类 Unix 示例单独视为兼容性缺陷，除非源码真实依赖这些假设

- 不做与 Windows 兼容性无关的代码风格、架构整洁度或通用重构建议

### 审计范围

本次审计聚焦会影响 Windows 终端用户的核心使用链路，按 6 层展开。

#### 1. 终端启动层

关注 PTY 创建、shell 选择、PATH 合并、批处理脚本与可执行文件解析，以及`node-pty`相关 Windows 分支。

重点检查：

- 是否假设 POSIX shell 总是可用

- 是否完整处理`.exe`、`.cmd`、`.bat`

- 是否正确处理 Windows PATH 分隔符和大小写

- 是否存在只在类 Unix 上成立的执行权限或登录 shell 逻辑

#### 2. CLI 与 agent 启动层

关注 CLI 注册、launcher 生成、agent shim、Hydra CLI 命令解析和 PATH 注入逻辑。

重点检查：

- 是否依赖 Unix shebang 或软链模型

- 是否遗漏`cmd.exe`或`pwsh.exe`包装

- 是否正确处理 Windows 用户 PATH、注册表、环境刷新广播

- 是否存在 CLI 名称解析、路径比较或大小写比较不稳的问题

#### 3. 进程检测与运行时观测层

关注前台工具检测、子进程树遍历、hook 接收、session/terminal 运行态识别等逻辑。

重点检查：

- 是否隐式依赖`ps`风格输出

- Windows 下 PowerShell/CIM 进程列表输出是否被稳健解析

- 命令行拆分与 CLI 类型识别是否受 Windows 引号、扩展名和包装器影响

#### 4. 路径、文件 URL 与资源定位层

关注盘符路径、反斜杠路径、file URL、资源目录、用户目录、extraResources、跨平台路径比较等逻辑。

重点检查：

- 是否把 POSIX 路径规则硬编码到 Windows 场景

- 是否会导致资源找不到、路径比较失真或 file URL 失效

- 是否存在 Unicode 路径、大小写、路径规范化边界条件

#### 5. 构建、安装与打包层

关注`package.json`脚本、安装后脚本、Electron Builder 配置、Windows 安装器目标和原生依赖解包策略。

重点检查：

- 是否要求 Windows 上默认不存在的 shell 或命令语义

- 安装/打包后资源路径是否与源码假设一致

- Windows 分发链路是否有明显漏配或易碎点

#### 6. 测试覆盖与回归保护层

关注平台条件测试、跳过 Windows 的用例、近期修复是否有稳定回归保护。

重点检查：

- 哪些模块显式承认 Windows 特殊性，但没有足够测试兜底

- 哪些测试通过 skip 掩盖了真实兼容性空洞

- 哪些近期修复点仍然容易再次退化

### 审计结论分级

为控制误报，本次审计统一使用三类结论。

#### 确认风险

从源码可直接推出在 Windows 上存在明确失败路径，或高概率出现行为错误。

#### 可疑风险

源码存在明显类 Unix 假设或分支缺失，但仅凭阅读还不能 100% 坐实，需要后续运行验证或补充上下文。

#### 已处理但脆弱

代码已经存在 Windows 特判或近期修复，但边界条件多、测试不足，或者实现方式容易再次回归。

### 风险级别

每个问题除了结论类型，还需额外给出开发优先级：

- 高：可能阻塞安装、启动、创建终端、启动 agent 或关键资源加载

- 中：不会完全阻塞，但会导致核心流程行为错误、不稳定或明显偏离 Windows 预期

- 低：边界条件、回归脆弱点、次级能力问题，短期不影响主路径

### 推荐审计方案

本次采用“模块分层审计”为主方案，结合全局模式扫描做入口、结合风险驱动排序做收敛。

#### 方案说明

1. 先用全局搜索建立候选点清单，包括平台判断、shell/命令执行、路径拼接、PowerShell/cmd、PATH 分隔符、扩展名处理、file URL、注册表和 Windows API。

2. 再按 6 层逐个阅读相关模块，区分“正确的平台分支”和“仍然带风险的类 Unix 假设”。

3. 最后结合测试与近期修复记录，对问题做定级和修复建议。

#### 不采用其他方案的原因

- 不采用纯 grep 式扫雷作为最终方案，因为误报会过多，无法直接支撑修复工作

- 不采用只看高风险模块的极窄审计，因为会漏掉测试覆盖、路径规范化等中频但真实存在的问题

### 审计方法

本次审计按“先广搜、再收敛、后定级”的顺序执行。

#### 第一轮：全局模式扫描

扫描以下模式：

- `process.platform`、`win32`、`darwin`、`linux`

- shell 与命令执行：`exec`、`spawn`、`spawnSync`、`execFile`、`execFileSync`

- Windows 命令扩展名：`.exe`、`.cmd`、`.bat`、`.ps1`

- PATH 与路径模式：`path.delimiter`、`;`、`:`、`path.win32`、`path.posix`

- 资源与 URL：`fileURLToPath`、`process.resourcesPath`、`extraResources`

- Windows 特有能力：注册表、环境广播、PowerShell、CIM、user32

这一轮只建立候选点，不直接输出风险结论。

#### 第二轮：模块内语义审查

对候选文件按模块读取代码，判断它属于以下哪类：

- 已正确适配 Windows

- 部分适配，但存在缺口

- 明显仍依赖类 Unix 假设

审查重点不是“有没有`win32`判断”，而是该判断是否真的覆盖了 Windows 下的执行语义、路径语义和资源语义。

#### 第三轮：测试与近期修复交叉验证

检查相关测试是否：

- 在 Windows 下直接 skip

- 只覆盖 happy path

- 缺少对近期修复问题的回归保护

如果源码看起来危险，但测试已经提供较强兜底，问题可降级为“已处理但脆弱”；如果测试本身暴露平台空洞，则可上调问题优先级。

#### 第四轮：定级与修复建议

只在源码证据足够明确时，才将问题定为“确认风险”。其余问题保留为“可疑风险”或“已处理但脆弱”，并附带后续验证建议。

### 误报控制原则

- 不把“存在 Windows 分支”本身视为问题

- 不把纯风格差异、命名差异或无用户影响的实现偏好当作兼容性风险

- 不把仅影响开发者本地构建、但不影响终端用户核心使用路径的问题抬成高优先级

- 不把文档示例自动等同于运行时依赖

- 不在缺少源码证据时夸大结论；无法坐实的问题必须降为“可疑风险”

### 交付格式

最终交付采用“开发修复导向”的结构，而不是体验报告。

#### 1. 审计摘要

简述本次覆盖范围、风险最集中的模块、哪些区域已有 Windows 适配基础。

#### 2. 问题清单

每条问题固定包含以下字段：

- 级别

- 分类

- 结论

- 文件定位

- 现象描述

- 源码证据

- 修复建议

- 测试建议

#### 3. 模块视图

按 PTY 启动链、CLI 注册链、进程检测链、路径资源链、安装打包链、测试保护链等维度反向汇总，便于按文件簇修复。

#### 4. 修复优先级建议

按以下顺序排序：

- 高风险确认问题

- 中风险确认问题

- 高风险可疑问题

- 已处理但脆弱问题

### 审计结果的使用方式

本 spec 的目标是定义一次“如何做 Windows 兼容性审计”的工作，而不是直接输出最终问题单。实现阶段完成后，产出应可以直接用于：

- 拆分修复任务

- 安排 Windows 回归测试补强

- 判断哪些模块需要继续做本机验证

- 评估是否需要单独补一轮 Windows 平台专项测试计划

### 成功标准

本轮设计完成后，应满足以下标准：

1. Windows 兼容性审计的范围、边界和判定口径已明确

2. 问题清单的字段和排序方式已明确，可直接承接后续审计结果

3. 已明确如何区分确认风险、可疑风险与已处理但脆弱问题

4. 已明确如何避免把正常平台差异误报为兼容性缺陷

5. 后续执行该审计时，不需要再重新讨论范围或输出格式

### 后续步骤

本 spec 确认后，下一步应进入实现计划阶段：

- 把本设计转成具体执行计划

- 按计划逐层审计源码

- 汇总并输出 Windows 兼容性问题清单
