### 项目面板排序模式下恢复整行拖拽设计

#### 背景

当前左侧`会话`面板中的项目行已经支持项目排序。此前围绕“标题文本可拖选复制”和“拖拽入口收缩到专用 handle”做过一轮设计探索,但在实际视觉落地里,左侧展开箭头附近的空间过于紧凑:

- 额外的 handle 会与展开箭头争夺有限的左侧空间

- 即使 handle 做得很窄,也容易让左侧层级拥挤

- 排序仍然是一个明确存在的模式,但不是常驻的高频文本交互场景

因此,本轮最终选择反向收口: 在排序模式下放弃标题文本拖选复制,恢复整行拖拽,换取更干净、更稳定的左侧结构。

#### 目标

- 在`projectPanelOrdering`启用时,恢复项目行整行拖拽

- 移除左侧独立 drag handle

- 保持展开箭头区域干净,不再叠加第二个小控件

- 保持项目行单击展开/收起与激活的现有主语义

- 不改变现有 pinned / unpinned 两组排序规则与跨组边界吸附规则

#### 非目标

- 不修改项目排序状态结构或持久化策略

- 不修改 pinned / unpinned 的分组语义

- 不引入额外的排序模式开关或全局编辑态

- 不在本次范围内扩展到 worktree 行或其他树节点

- 不在本次范围内保留项目标题的鼠标拖选复制能力

#### 用户确认的行为边界

- 放弃项目标题的鼠标拖选复制

- 在排序模式下恢复整个项目标题控件范围都可拖拽

- 不再保留左侧专用 handle

- 不再需要`panel_project_reorder`这类独立 handle 文案

- 展开箭头仍然保留原有视觉和点击语义

- 项目标题单击仍然保留现有主语义: 展开/收起并按现有规则激活项目

#### 现状

当前`ProjectTree`里已经接入过一版独立 handle 方案,主要包含:

- `SortableProjectRow`把 activator/listeners 绑定到专用 handle

- `ProjectRow`里增加了左侧窄 handle 的渲染

- 标题文本区额外引入了真实文本选区保护逻辑

这些改动虽然解决了文本拖选与拖拽冲突,但也带来了新的视觉成本: 左侧箭头附近空间过挤,且多了一个低频语义控件。

#### 约束

- 改动应尽量收敛在`ProjectTree`与项目行交互层,不要扩散到排序数据层

- 现有排序规则必须保持不变,避免把一次交互改动变成排序逻辑回归

- 项目行恢复整行拖拽后,右侧 pin / task / 新建 worktree 等按钮仍必须保持事件隔离

- 项目标题应明确设为不可选文本,避免看起来可选但实际会触发拖拽

#### 方案比较

候选方案主要有三类:

1. 保留整行拖拽,并禁止项目标题文本选择

2. 保留专用 handle,标题文本可选

3. 引入明确的排序模式编辑态,平时不提供拖拽

最终选择方案 1。

原因:

- 方案 1 的左侧结构最干净,展开箭头语义最清楚

- 方案 2 在这个布局密度下仍然容易让左侧拥挤

- 方案 3 从产品角度更完整,但超出本轮范围,会引入额外状态与入口设计

#### 最终方案

##### 项目标题文本区

- 在排序模式下,项目标题文本区明确视为不可选文本

- 标题文本区不再支持原生鼠标拖选复制

- 标题文本区继续保留现有单击行为: 展开/收起并按现有规则激活项目

##### 排序入口

- 在`projectPanelOrdering`启用时,整行恢复为唯一拖拽入口

- 不再渲染左侧专用 handle

- `SortableProjectRow`的 activator/listeners 重新挂回项目行主容器

##### 左侧结构

- 展开箭头左侧不再存在单独拖拽控件

- 箭头、标题、状态徽标与右侧操作按钮恢复到更干净的行内结构

##### 事件语义

- 单击项目标题文本区:

  - 展开/收起项目

  - 按现有规则激活项目

- 在排序模式下,从项目行任意非按钮区域按下并拖动:

  - 进入项目排序语义

- 右侧 pin / task / 新建 worktree 等按钮:

  - 继续保留`stopPropagation`

  - 不参与行拖拽

#### 组件职责边界

##### 排序规则层

- `ProjectPanelOrderingProps`

- `onMove(projectId, targetGroup, targetIndex)`

- pinned / unpinned 两组的组内排序与跨组边界吸附规则

以上内容全部保持不变。

##### sortable 接线层

- `SortableProjectRow`继续负责从`useSortable()`获取拖拽能力

- 但 activator/listeners 重新回到项目行主容器

- 不再使用专用 handle 的 activator ref

##### 项目行渲染层

- `ProjectRow`删除左侧 handle

- `ProjectRow`标题文本改为不可选

- `ProjectRow`继续保留现有箭头、标题、状态徽标、右侧按钮等结构

#### 可访问性

- 不再需要独立 handle 的 aria label 与 tooltip

- 展开箭头和右侧按钮的 focus-visible 行为保持不变

- 不要求本次扩展键盘排序能力

#### 测试与验收

##### 自动化测试重点

- 排序模式下不再渲染独立 reorder handle

- 点击标题仍能展开/激活

- pin / task / 新建 worktree 按钮行为不回归

- 现有 pinned / unpinned 的跨组排序语义不回归

##### 手工验证重点

- 排序模式下,左侧只有展开箭头,没有额外拖拽控件

- 项目标题文本不可拖选

- 从项目行空白区或标题区起手都可以发起排序拖拽

- 单击项目标题时,项目仍按当前行为展开/收起并激活

- 右侧按钮行为无回归

#### 风险与后续

本方案的代价是明确放弃标题文本拖选复制能力。

如果后续又重新出现“项目标题经常需要复制”的真实使用场景,更合适的方向不是重新塞回左侧小 handle,而是单独设计更明确的排序编辑态。
