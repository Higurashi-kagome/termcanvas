### 项目面板标题拖选与排序入口解耦设计

#### 背景

当前左侧`会话`面板中的项目行已经支持项目排序,但拖拽起点直接挂在整行上。

这在排序功能可用的同时,也带来了一个更高频的交互冲突:

- 用户有时需要在项目标题区域做原生鼠标拖选复制

- 标题上的水平拖选手势会被整行拖拽捕获,误触发排序

- 排序本身是低频操作,不应优先抢占项目标题这块热区

换句话说,当前问题的重点不是“拖拽灵敏度不合适”,而是“项目标题区域承担了过多语义”。

#### 目标

- 让项目标题文本区支持原生鼠标拖选复制

- 避免在标题文本区拖选时误触发项目排序

- 保持项目排序能力存在,但把它收缩到更明确的次级入口

- 保持项目行单击展开/收起与激活的现有主语义

- 不改变现有 pinned / unpinned 两组排序规则与跨组边界吸附规则

#### 非目标

- 不修改项目排序状态结构或持久化策略

- 不修改 pinned / unpinned 的分组语义

- 不在本次范围内处理“双击项目名是否选词”这类浏览器文本选择细节

- 不在本次范围内引入“限制水平拖拽”或“仅纵向手势才能起拖”的额外策略

- 不在本次范围内扩展到 worktree 行或其他树节点

#### 用户确认的行为边界

- 排序是低频操作,不应继续占用整个项目标题控件范围

- 项目标题文本区允许原生鼠标拖选复制

- 项目标题文本区上的单击仍然保留现有主语义: 展开/收起并按现有规则激活项目

- 项目标题文本区形成实际文本选区后,这次手势应优先被视为文本选择,不再触发行点击或排序

- 项目排序入口改为项目展开箭头左侧的专用 handle

- handle 采用固定槽位,但图标只在 row hover / focus / 正在拖拽时显现

- 本轮先不处理“双击项目名选择文本”的限制

- 本轮先不做“限制水平拖拽”的补充优化

#### 现状

当前`ProjectTree`里的项目排序接线方式大致如下:

- `SortableProjectRow`通过`useSortable()`拿到 sortable 能力

- `ProjectRow`接收一组`rowDragProps`

- 这组 props 直接展开到项目行主容器上

- 结果是整个项目行都会响应排序拖拽起点

与此同时,项目行主容器本身还承担了这些语义:

- 单击展开/收起

- 激活项目

- 右键菜单

- 右侧 pin / task / 新建 worktree 等 hover 按钮

这意味着当前同一热区里叠加了“导航”“文本交互”“排序”三种不同优先级的行为,冲突不可避免。

#### 约束

- 改动应尽量收敛在`ProjectTree`与项目行交互层,不要扩散到排序数据层

- 现有排序规则必须保持不变,避免把一次交互改动变成排序逻辑回归

- 项目行不应因为支持标题拖选复制而整体失去可点性

- 新增排序入口后,不应造成项目行左右布局抖动

- handle 的可访问性需要与现有 icon button 体系兼容

#### 方案比较

候选方案主要有三类:

1. 保留整行拖拽,只加强拖拽启动阈值或限制为纵向手势

2. 让标题文本区退出拖拽,但不提供清晰的显式 handle,仅保留隐式非文本拖拽区

3. 在左侧增加固定槽位,用专用 handle 承担排序拖拽

最终选择方案 3。

原因:

- 方案 1 只能缓解误拖拽概率,不能把标题文本区从排序语义里彻底解放出来

- 方案 2 虽然能减少冲突,但拖拽热区会变成隐式规则,发现性和可解释性都偏弱

- 方案 3 能把“标题文本选择”和“排序拖拽”拆成两个明确入口,边界最清楚,也最符合“高频文本交互优先、低频排序次之”的原则

#### 最终方案

##### 标题文本区

- 项目标题文本区是一个正式的文本交互区,支持原生鼠标拖选复制

- 标题文本区不再承担排序拖拽起点语义

- 标题文本区上的单击继续保留现有行为: 展开/收起并按现有规则激活项目

- 只要从标题文本区开始的手势最终形成了真实文本选区,这次手势就应被判定为文本选择,不再回流成项目行点击

##### 排序入口

- 在项目展开箭头左侧增加一个固定宽度的槽位

- 槽位始终占位,即使 handle 图标未显示,也不让标题、箭头、状态徽标在 hover 时左右跳动

- 排序拖拽只能从这个专用 handle 发起

- 整行主容器与标题文本区都不再挂 sortable listeners

##### handle 显隐规则

- handle 图标在项目行 hover 时显示

- handle 图标在项目行或其子控件获得键盘焦点时显示

- handle 图标在当前项目正在被拖拽时保持显示

- 非上述状态下,槽位保留,handle 图标隐藏或弱化,避免制造额外视觉噪音

##### handle 视觉规则

- handle 使用低对比度的 grip 类图标

- 视觉层级低于项目标题,也不抢过 pin / task / plus 这类右侧操作按钮的注意力

- hit target 仍按按钮处理,与现有 icon button 的可点性保持一致

- aria label 与 tooltip 语义明确表达“拖拽排序项目 <项目名>”

#### 事件语义

- 单击项目标题文本区:

  - 展开/收起项目

  - 按现有规则激活项目

- 从项目标题文本区按下并拖动:

  - 如果形成真实文本选区,本次手势视为文本选择

  - 不触发展开/收起

  - 不触发激活

  - 不进入排序拖拽

- 从专用 handle 按下并拖动:

  - 仅进入项目排序语义

  - 不触发展开/收起

  - 不依赖标题文本区参与拖拽

- 从项目行非文本空白区单击:

  - 继续保留现有项目行点击行为

这样一来,用户心智会比较稳定:

- 想复制标题,去标题文字上拖选

- 想展开项目,点标题或行空白区

- 想排序项目,去左侧 handle

#### 组件职责边界

##### 排序规则层

- `ProjectPanelOrderingProps`

- `onMove(projectId, targetGroup, targetIndex)`

- pinned / unpinned 两组的组内排序与跨组边界吸附规则

以上内容全部保持不变。

本次不是修改排序规则,而是修改“谁可以发起拖拽”。

##### sortable 接线层

- `SortableProjectRow`继续负责从`useSortable()`获取拖拽能力

- 但注入给`ProjectRow`的接口应从“整行 drag props”收缩为“专用 handle 的 drag props / activator ref”

- 如果 dnd-kit 的 activator ref 能力可用,应将 activator 明确绑定到 handle,而不是项目行主容器

##### 项目行渲染层

- `ProjectRow`负责新增左侧固定槽位

- `ProjectRow`负责渲染 handle 的显隐状态

- `ProjectRow`负责把标题文本区从拖拽热区中剥离出来

- `ProjectRow`继续保留现有箭头、标题、状态徽标、右侧按钮等结构

##### 文本选择判定层

- 标题文本区需要具备“文本拖选优先于点击”的判定能力

- 这部分判定应局限在项目标题交互本身

- 不应把这套判定扩散到 worktree 行或其他树节点

#### 可访问性

- handle 必须有明确的可访问名称

- handle 需要保留与现有 icon button 一致的 focus-visible 样式

- 不要求本次扩展键盘排序能力,但不能破坏现有键盘 focus 行为

- 当 handle 获得焦点时,其显现方式应稳定,避免焦点刚进入时目标抖动消失

#### 测试与验收

##### 自动化测试重点

- 排序 listeners 不再挂到项目行主容器

- handle 作为唯一排序入口存在

- 点击标题仍能展开/激活

- 点击 handle 不会触发展开/激活

- pin / task / 新建 worktree 按钮行为不回归

- 现有 pinned / unpinned 的跨组排序语义不回归

##### 手工验证重点

- 从项目标题文字上水平拖选时,能稳定形成文本选区

- 拖选标题时不会误触发排序

- hover 项目行时 handle 显现,但整行布局不跳动

- 从 handle 发起拖拽时,排序体验与当前版本一致

- 行空白区点击仍保持现有展开/激活体验

#### 风险与后续

本方案刻意把范围控制在“拖拽入口解耦”上,因此有两类问题被明确留到后续:

- 双击项目名时的文本选择细节与语义限制

- 基于水平 / 垂直方向的额外拖拽启动优化

如果首版 handle 解耦已经足够解决标题拖选冲突,这两类问题可以继续保持延后。

如果后续仍观察到 handle 起拖过于敏感,再单独评估是否叠加轻量启动阈值,但那应作为拖拽体验优化,而不是本设计的主解决方案。
