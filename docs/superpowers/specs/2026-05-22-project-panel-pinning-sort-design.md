### 项目面板置顶与排序设计

#### 背景

当前左侧`会话`面板中的项目列表完全按`projectStore.projects`现有顺序渲染。

这带来两个问题:

- 常用项目无法固定在前面

- 用户无法按自己的工作节奏重排项目顺序

TermCanvas 的左侧项目面板已经承载了项目、worktree、终端的主要导航职责,因此项目顺序本身已经不仅是“装饰性 UI”,而是直接影响浏览效率的工作区组织方式。

本设计的目标是为项目面板补上两个能力:

- 用户可以显式将项目置顶

- 用户可以通过拖拽调整项目顺序

#### 目标

- 支持通过项目行上的按钮切换项目置顶状态

- 支持置顶项目之间的拖拽排序

- 支持非置顶项目之间的拖拽排序

- 支持跨越两组边界拖拽,但拖拽本身不改变置顶状态

- 项目置顶状态与项目面板顺序跟随工作区状态一起保存

- 仅影响左侧项目面板的显示顺序,不强行改变其他视图的项目顺序语义

#### 非目标

- 不在项目目录、仓库目录、worktree 目录写任何状态文件

- 不把项目置顶状态做成本机`localStorage`偏好

- 不通过拖拽隐式切换项目的置顶状态

- 不修改右键菜单、项目展开/收起、创建 worktree、任务抽屉等现有交互语义

- 不在本次范围内扩展到`历史`面板或其他项目视图

#### 用户确认的行为边界

- 项目行增加一个`置顶`按钮,样式与现有`标记`按钮一致,仅更换图标

- `置顶`按钮位于`标记`按钮左侧

- 新项目默认进入非置顶组末尾

- 取消置顶的项目进入非置顶组末尾

- 置顶按钮负责切换项目是否置顶

- 拖拽只负责调整顺序,不负责切换项目是否置顶

- 普通项目拖到置顶组区域时,不变成置顶,而是吸附到普通项目第一位

- 置顶项目拖到普通组区域时,不取消置顶,而是吸附到置顶项目最后一位

#### 现状

当前左侧项目树的数据链路大致如下:

- `useProjectStore().projects`保存项目事实数据

- `buildProjectTree()`按`projects`顺序构建`ProjectGroup[]`

- `ProjectTree`直接按传入数组顺序渲染

当前系统里已经有两种相关状态模型:

- 工作区状态持久化,用于保存项目/终端/画布等工作区事实数据

- `leftPanelUiStateStore`,用于保存折叠/展开这类本机左侧面板 UI 偏好

本次需求同时涉及“顺序”和“置顶”,语义上更接近工作区组织方式,不适合继续放入只面向本机 UI 偏好的`leftPanelUiStateStore`。

#### 约束

- 数据必须跟随工作区状态保存,但不能写入项目目录

- 左侧项目面板顺序不能直接污染所有消费`projects`数组的视图

- 需要兼容项目新增、删除、重命名路径、工作区恢复等现有生命周期

- 拖拽交互要尽量贴合现有 React 组件结构,避免为一个列表排序需求引入大范围 UI 重写

#### 方案选择

候选方案有三类:

1. 直接修改`projectStore.projects`数组顺序,把置顶和排序都塞回项目事实顺序

2. 新增一份独立的“项目面板排序元数据”,左侧项目面板渲染前做投影排序

3. 把置顶和排序做成类似`leftPanelUiStateStore`的本机 UI 偏好

最终选择方案 2。

原因:

- 方案 1 实现表面最直接,但会把左侧面板的排序语义扩散到所有后续消费者

- 方案 3 与“跟随工作区保存”的需求冲突,而且会导致换工作区或换机器时状态不一致

- 方案 2 能把“数据跟工作区走”和“影响面只收敛到左侧项目面板”同时满足

#### 状态模型

建议在工作区状态中新增一份左侧项目面板排序元数据,但不把它并入项目事实字段。

建议结构:

```ts
interface ProjectPanelOrderState {
  pinnedProjectIds: string[];
  unpinnedProjectIds: string[];
}
```

说明:

- `pinnedProjectIds`按显示顺序保存当前置顶项目 id

- `unpinnedProjectIds`按显示顺序保存当前普通项目 id

- `projectId`继续使用现有运行时项目 id

- 不在`ProjectData`上直接增加`pinned`或`order`字段

选择双数组而不是`Record<projectId, { pinned, index }>`的原因:

- 更接近真实渲染结果

- 组内重排时更新最直接

- 置顶/取消置顶本质上就是在两个数组间移动元素

- 更容易表达“普通组第一位”“置顶组最后一位”这类边界吸附规则

#### 持久化策略

这份元数据跟随工作区状态保存,但不写进任何项目目录。

具体原则:

- 工作区保存时,一并序列化`ProjectPanelOrderState`

- 工作区恢复时,恢复该状态并立即参与左侧项目面板排序

- 不使用`localStorage`

- 不额外创建磁盘侧面板配置文件

恢复后需要做一次归一化:

- 去掉已不存在的项目 id

- 去掉重复 id

- 当前存在但未出现在两组数组中的项目,自动补到`unpinnedProjectIds`末尾

这样可以保证旧工作区、异常状态、增删项目后的恢复结果始终稳定可解释。

#### 渲染模型

左侧项目面板渲染前先做一次投影排序:

1. 从`projectStore.projects`读取当前项目事实列表

2. 按`ProjectPanelOrderState`重建左侧项目面板专用顺序

3. 先输出置顶组,再输出普通组

4. 把重排后的项目列表作为`buildProjectTree()`的输入,不在`ProjectTree`内部再做二次排序

这意味着:

- 左侧项目面板看到的是显式排序后的顺序

- 其他直接消费`projectStore.projects`的视图仍保留现有语义

- 本次需求的影响边界保持清晰

#### 交互设计

##### 置顶按钮

- 在项目行现有按钮区新增一个`置顶`按钮

- 样式复用当前`标记`按钮的尺寸、hover、激活态与显隐逻辑

- 图标改为 pin 图标

- 位置放在`标记`按钮左侧

- 已置顶项目显示激活态,未置顶项目显示普通态

按钮行为:

- 点击未置顶项目: 将项目从普通组移到置顶组末尾

- 点击已置顶项目: 将项目从置顶组移到普通组末尾

##### 分组表现

- 列表在视觉上仍是一条连续树

- 置顶组排在上方,普通组排在下方

- 两组之间增加轻量视觉分隔,建议使用 4 到 6px 的垂直间距或极淡分隔线

分隔的作用不是引入新层级标题,而是帮助用户理解拖拽边界吸附语义。

##### 拖拽规则

- 置顶项目之间可以自由排序

- 普通项目之间可以自由排序

- 拖拽穿越两组边界时允许悬停,但不改变置顶状态

- 普通项目拖入置顶区域时,落点吸附为普通组第一位

- 置顶项目拖入普通区域时,落点吸附为置顶组最后一位

规则总结:

- 按钮改分组

- 拖拽改顺序

- 跨组拖拽只做边界吸附,不做状态切换

##### 其他交互兼容性

- 项目行点击展开/收起逻辑保持不变

- 右键菜单保持不变

- `标记`按钮逻辑保持不变

- 创建 worktree 按钮逻辑保持不变

- 项目行焦点和键盘选中逻辑保持现有行为

#### 拖拽库选型

仓库当前没有现成的列表排序依赖。

现有拖拽实现主要分为两类:

- 面向画布元素的原生`pointermove`拖拽

- 面向文件或 pin 的原生`dragstart` / `drop`

本次候选库主要有:

1. `@dnd-kit`

2. `@hello-pangea/dnd`

3. 自己基于原生 pointer 事件手写列表排序

最终建议使用`@dnd-kit`。

原因:

- 适合 React 组件树内的排序场景

- 支持`SortableContext`、`useSortable`、`DragOverlay`

- 支持垂直轴限制

- 支持自定义 collision / drop 逻辑,更容易表达“跨组悬停但只吸附到允许边界”的规则

- 比手写 pointer 排序更省维护成本

不优先选`@hello-pangea/dnd`的原因:

- 它对标准列表重排很顺手

- 但本次规则不是典型的“同列表随处插入”或“跨列表直接移动”

- “跨组拖拽允许进入区域,但不改分组,只落到边界位置”这类定制语义在`@dnd-kit`下更自然

不建议手写 pointer 排序的原因:

- 要自己补拖拽命中、占位动画、拖拽预览、键盘可访问性

- 对这次需求而言投入和维护成本都偏高

#### 状态更新规则

建议围绕`ProjectPanelOrderState`提供一组纯状态操作:

- `normalizeProjectPanelOrder(projectIds)`

- `pinProject(projectId)`

- `unpinProject(projectId)`

- `reorderPinned(projectId, targetIndex)`

- `reorderUnpinned(projectId, targetIndex)`

- `moveUnpinnedToBoundaryStart(projectId)`

- `movePinnedToBoundaryEnd(projectId)`

行为定义:

- `pinProject(projectId)`:

  - 先从两组数组中移除该项目 id,避免重复

  - 再追加到置顶组末尾

- `unpinProject(projectId)`:

  - 先从两组数组中移除该项目 id,避免重复

  - 再追加到普通组末尾

- 普通项目拖进置顶区域:

  - 仍留在普通组

  - 移动到普通组索引 0

- 置顶项目拖进普通区域:

  - 仍留在置顶组

  - 移动到置顶组末尾

- 删除项目:

  - 从两组数组中同时清理

- 新增项目:

  - 追加到普通组末尾

建议主要改动边界如下:

- `src/types/index.ts`

- `src/components/ProjectTree.tsx`

- `tests/session-panel-model.test.ts`

职责划分建议:

- `sessionPanelModel`或其上游负责把事实项目列表投影成左面板顺序

- `ProjectTree`负责按钮、拖拽交互和视觉反馈

#### 风险与对策

##### 运行时项目 id 稳定性

风险:

- 如果未来工作区恢复时项目 id 重建规则变化,排序元数据可能丢失匹配

对策:

- 本次先沿用现有项目 id 作为排序键

- 在恢复链路里做归一化,确保异常时至少回退到普通组末尾

- 后续如发现 id 稳定性不足,再单独评估引入路径级稳定键

##### 左侧项目面板顺序与其他视图不一致

风险:

- 其他地方若仍读`projectStore.projects`,顺序可能与左侧面板不同

对策:

- 本次明确将该能力限定为左侧项目面板显示顺序

- 若后续其他视图需要复用,应显式接入同一投影排序,而不是隐式依赖

##### 拖拽命中边界不直观

风险:

- 用户可能不理解为什么拖进另一组后没有改置顶状态

对策:

- 用组间轻量分隔增强边界可见性

- drag preview 与占位态要明确表现最终落点

- 置顶状态切换始终由 pin 按钮独占

##### 工作区旧状态兼容

风险:

- 旧工作区文件没有排序元数据

对策:

- 恢复时缺少该字段就自动初始化为空

- 归一化后把全部当前项目补进普通组末尾

#### 测试策略

需要覆盖以下场景:

1. 新项目加入:

    - 默认追加到普通组末尾

2. 点击置顶:

    - 项目进入置顶组末尾

    - 再次点击后进入普通组末尾

3. 置顶组内拖拽:

    - 顺序正确更新

4. 普通组内拖拽:

    - 顺序正确更新

5. 普通项目拖入置顶区域:

    - 项目仍属于普通组

    - 项目成为普通组第一位

6. 置顶项目拖入普通区域:

    - 项目仍属于置顶组

    - 项目成为置顶组最后一位

7. 删除项目:

    - 两组数组中的对应 id 被清理

8. 恢复旧工作区:

    - 缺少排序元数据时不报错

    - 当前项目全部进入普通组末尾

9. 持久化 round-trip:

    - 保存后再恢复,置顶和顺序保持一致

10. 左侧项目面板投影排序:

    - 左侧面板顺序符合元数据

    - 其他未接入视图不被强制重排

#### 里程碑

1. 为工作区状态新增项目面板排序元数据

2. 在`projectStore`中接入置顶、取消置顶、组内重排与归一化逻辑

3. 在左侧项目树接入 pin 按钮和拖拽排序

4. 接入工作区持久化与恢复

5. 补充状态与渲染测试

6. 手工验证两组排序、跨组边界吸附和工作区恢复

#### 结论

本方案把项目置顶与排序定义为“跟随工作区的左侧项目面板组织方式”,而不是项目目录文件或本机临时偏好。

它的核心取舍是:

- 置顶状态由按钮显式切换

- 拖拽只负责顺序调整

- 跨组拖拽允许进入边界区域,但只做吸附,不改项目分组

- 持久化跟工作区走,影响范围先收敛在左侧项目面板

在这个边界下,功能语义清晰,实现可控,也为后续把同一排序能力复用到其他项目视图保留了空间。
